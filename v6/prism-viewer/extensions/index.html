Writing a Prism viewer extension

An extension adds to the viewer: engine pieces (color themes, behaviors), operations with their commands, annotations, tracks in the sequence, skills for the assistant, and views. It is a plain object that you put in the spec’s extensions list. The extensions are code in the Mol* repository. The types are the viewer’s own, and there is no stability promise beyond the repository’s.

Work in progress

apps/prism-viewer/src/extensions.ts lists the extensions the app ships: model quality, model and geometry export, video export, Zenodo, assembly symmetry, membrane orientation, Kinemage and the data-only ones.

An extension should start with operations, commands and skills, and add views only where a view is needed.

ViewerExtension

Section titled “ViewerExtension”
FieldWhat it is
idLowercase words joined by dashes. Every part id starts with it. It cannot be the id of a core API area.
titleFor people.
pluginThe engine side: { registry?, behaviors?, config? }. Registry entries (color themes, representations, formats), behaviors and config items.
apiIts API areas, by area id: { [areaId]: (ctx) => new MyArea(ctx) }. Each is made once. The operation ids start with the area id.
commands(api) => CommandDefinition[]. Called once its operations exist.
annotationsAnnotationProvider[]: what it can show of a structure. They appear in annotations.list and annotations.apply.
sequenceSequenceBehavior[]: tracks and menus in the sequence view. See below.
skillsViewerSkill[]: tools for the assistant over its operations. A skill, never a core tool.
ui(ctx) => ViewerExtensionUI: its views. A function, so the views can be a chunk of their own.
settingsReserved for its group in Settings. Not shown yet.

builtIn and contributes are for the viewer’s own features: only they may add operations to core areas such as load and canvas. An extension adds an area of its own.

An extension is headless-safe when plugin, api, commands, annotations, sequence and skills import no DOM. Keep the DOM in ui.

Parts and ids

Section titled “Parts and ids”

Anything with an id that the viewer registers is a part: a tab, a section, a toolbar item, an overlay, a sequence behavior. A part id is <owner>.<kind>.<name>, where the owner is the extension id:

The kinds are tab, section, row, selection-action, node-action, toolbar, overlay, command, tool, skill, sequence, api and settings. Operation ids and command ids are their own: <area>.<verb>. A duplicate id is an error at creation, and the message names both owners.

Views

Section titled “Views”

ui returns any of these. Each id is a part id with the matching kind.

FieldWhat it is
sectionsA section { id, slot, title, icon?, order?, keywords?, render } in one of the viewer’s slots.
tabsA tab { id, title, icon, dock?, order?, render } for a large view of its own.
overlaysA card over the canvas { id, title, render }, opened by a toolbar item or a command.
toolbarAn item { id, icon, title, command?, overlay?, group?, order?, place?, visible? } that runs a command or opens one of its overlays.
rowsRows in the Structure tab’s tree { id, when(node), whenChanged?, render }, under the nodes when holds for (a structure’s assembly symmetry).
selectionActionsRows of the selection bar’s menu { id, title, hint?, icon?, order?, command?, run? }: what to do with the selection, run as a command or by run.
nodeActionsRows of the scene tree’s node menus, which the inspector shows too, { id, title, icon?, order?, kinds, when?(node), run(node) }: on the node kinds in kinds that pass when, after the node’s own rows and before Remove. run gets the node.

The slots are a closed list that the viewer owns. An extension cannot add rail buttons or cards of its own beyond these.

SlotWhere a section goes
home.importHome, under the loading actions.
selectionThe Selection tab.
exportThe export card.
canvas-settingsThe canvas settings card.
animationThe animation card.
settingsSettings, after the viewer’s groups.
inspector:<kind>The inspector of a node kind, such as inspector:structure or inspector:component.

render is a Prism view, domView(...) from @molstar/prism-ui. The context ui receives has api (the API as the person), sources (read-only states over the plugin) and managers. It has no plugin, so a view changes the scene through operations.

An operation, a command

Section titled “An operation, a command”

An area is a class with its operations as fields. The area’s id is its key in api. This one frames the ligands of a structure by composing two core operations:

The params of an operation are one parameter definition (ParamDefinition from @molstar/core/util/param-definition). The command’s form, the assistant’s tool fields and the validation all derive from it. Besides history: false, the definition can say:

FieldMeaning
read: trueIt changes nothing: no history step.
undoable: falseThe history cannot restore it, for example an upload: no checkpoint. The assistant asks every time.
approval'network', 'upload' or 'destructive': the assistant asks before running it. See Assistant.
addresses(values)For network: the addresses a call reaches, so the assistant can check them.
modulesWhat it needs of the host: canvas, files, network, storage, page. Without it, it fails with unavailable.
when(ctx)true or the reason it cannot run now.
exists(values, ctx)For operations that create something: a message when it exists already, and the run does nothing.

The declare module block types the area for scripts that import the extension. An operation’s own calls go through ctx.api, which is part of its step: if show were an undoable operation, the select and the camera calls would be inside its one undo step.

Lazy extensions

Section titled “Lazy extensions”

A heavy extension can load on first use. LazyViewerExtension has the same id and title, a load function, and a stub that says what it will bring:

The stub is what exists before the load: operations, command titles, placeholders for views, and skills for the assistant’s catalog. Calling a stub operation, running a stub command or disclosing its skill loads the chunk as a task in the status column, swaps the real extension in, and replays what asked for it.

  • A stub must declare every part, operation and command the extension brings. A loaded extension that brings what the stub did not declare, or lacks an operation it declared, or declares different flags (read, undoable, approval, modules), fails the load. Activation is all or nothing: the stub is put back and a later call tries again.
  • stub.owns lists transformer ids, formats, file extensions, representations and themes that the extension answers for. Opening a file with one of its extensions, or a .molj session that needs one of its transformers, loads the extension first.
  • preload: true loads it during creation, before ready, still as a chunk of its own.
  • Overrides apply to the stub’s parts too, so they are checked when the spec is created.

@molstar/prism-viewer/features/lazy shows the pattern: the heavier built-in features as stubs whose load imports the feature’s module. Put the stub in a module that does not import the rest of the extension, or the chunk is loaded with the stub.

Sequence tracks

Section titled “Sequence tracks”

The sequence band shows one structure at a time; the structure tree has a Sequence node under every structure, whose children are its tracks. A track provider is how an extension adds sequence data: it says what its track is and when it applies, and the viewer puts it in and takes it out, per structure. The person adds it (Add track), removes and hides it; the agent does the same through sequence.track.add, .remove, .hide and .show. Each change is a step.

MemberWhat it is
id, label, orderThe id is <extension id>.sequence.<name>; the label names it in the tree and under Add track; order places its track (ruler 0, letters 10, secondary 20).
trackIts track’s ref in the document (start it with the extension’s id).
applies(structure)The structure carries its data. Read only the structure and what the viewer holds: a provider fetches nothing.
shownIn by default; false for a track only offered under Add track.
build(ctx)Its data nodes and its one track (Seq* document nodes) over ctx.structure, ctx.complex (the complex ref a computed node names) and ctx.letters.
menu, legendThe track’s menu (colorings of the 3D view by theme; the first is its icon in the band’s gutter) and its legend blocks, shown while it is in.
whenChangedA state told when applies may answer otherwise without a new structure (a property computed later).

List providers in the extension’s sequence.tracks. The viewer’s own (ruler, letters, secondary structure) are providers too, in spec.sequence.tracks, and overrides replaces or removes any of them by id.

Sequence behaviors

Section titled “Sequence behaviors”

For what is not a track, a rule that follows the scene, a sequence behavior adds to the document by patch. It reads what the sequence shows and proposes changes. List them in the extension’s sequence.behaviors.

MemberWhat it is
id, titleThe id is <extension id>.sequence.<name>; the host checks it.
attach(ctx)Starts the behavior and returns its dispose function.
ctx.shownA ReadonlyState of what the document shows. A new value for each document (another structure, another letter theme), undefined for nothing. It carries the structure, the complex ref, the data node, the section and the track to put yours after (none: the end).
ctx.patch(shown, ops)Applies Seq* operations to that document, all or nothing. It returns false and does nothing if the document was replaced meanwhile.
ctx.offer(offer)Gives the track menus (menus, by track ref) and the legend blocks (legend). undefined withdraws them.

A new document has none of the behavior’s nodes, so the behavior adds them again whenever shown changes. Give its nodes refs that start with its id, and make patch insert them.

An example: model quality

Section titled “An example: model quality”

packages/extensions/model-archive/src/prism-viewer.ts is the model-archive extension, shown in the app. It makes the quality scores of predicted models visible: pLDDT and QMEAN.

It uses four of the fields and no views:

  1. plugin.registry registers the two color themes with the engine, so representation.color({ theme: 'plddt-confidence' }) works for every caller.
  2. annotations are two providers, plddt and qmean, each with isApplicable(structure) and an apply that calls ctx.api.representation.color(...). A provider that applies through other operations is part of the step of annotations.apply. api.annotations.list() tells which a structure carries, and api.annotations.apply({ annotation: 'plddt' }) colors it.
  3. commands make “Color by pLDDT” and “Color by QMEAN” from annotations.apply with the annotation value fixed. operationCommand gives the command its form, its availability and its undo entry.
  4. sequence has a track provider: a pLDDT track under the viewer’s tracks, in by default for a structure that carries pLDDT.

The provider, reduced:

The track’s menu item colors the 3D view with the theme. The legend blocks appear in the sequence legend card. The viewer itself knows nothing of pLDDT: the whole feature is in this one package, and the app turns it on by listing it in MolstarViewerExtensions.

The extension has no skill and no view yet, and the pairwise (PAE) plot waits for a view of its own. The other ported extensions (apps/prism-viewer/src/extensions.ts) follow the same shape: model and geometry export with Export sections, video export and Zenodo as lazy extensions with stubs (prism-viewer-stub.ts), assembly symmetry, ANVIL’s membrane and Kinemage as operations, commands and skills.
