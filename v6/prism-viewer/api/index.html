The Prism viewer API

viewer.api is what scripts, embedding pages, the viewer’s own commands and the assistant all call. It has one object per area, and each area has operations as methods:

Every operation takes one object of values and returns a promise of a result. Values you leave out take their defaults, so api.component.add({ target: 'resn HEM' }) is a whole call. Operations a feature adds to a core area (the loaders’ load.entry) are optional members (api.load.entry?.(…)); api.run('load.entry', …) reaches them by id. A second optional argument is { signal?: AbortSignal; copy?: boolean }.

Operations never throw. A failure is a result.

Results

Section titled “Results”
FieldWhenMeaning
okalwaystrue or false.
didokWhat happened, in one line.
changedokWhat a reader should read again: { nodes?, selection?, view?, sequence? }.
unchangedoktrue when it was already so. Nothing changed and no history step was made.
valueokThe data of a read, or what the operation made.
warningsokThings worth knowing.
nextokAn obvious next step, when there is one.
code!okWhy it failed (below).
message!okWhat went wrong, for a person.
hint!okWhat to do instead.

An operation states a desired state: running representation.color with the same values twice changes nothing the second time, and the second result is unchanged. An operation that creates something checks whether it exists: load.entry for an entry that is loaded, or component.add for a component that is there, does nothing and says so. Pass { copy: true } as the second argument to get another.

Failure codes:

CodeMeaning
invalidThe values are wrong.
blockedNot possible now, for example Undo with nothing to undo.
unavailableThe host lacks what the operation needs, such as a canvas headless.
not-foundSomething it names does not exist, or a target selected nothing.
ambiguousMore than one thing matches.
confirmAsk the person first, then call again.
abortedThe signal was aborted.
failedIt ran and failed. A failed or aborted run restores what it changed.

Areas

Section titled “Areas”

The operation component.add is api.component.add(...), and it is the same operation the command menu, the run log and the assistant call. A hyphen in an operation id is camel case on the area: history.undo-turn is api.history.undoTurn, superpose.tm-align is api.superpose.tmAlign. These are the areas the viewer has today. The core’s (load, session, select, focus, highlight, camera, canvas, settings, history, view) are always there. The built-in features’ areas (structure, contents, component, representation, styles, annotations, trajectory, volume, measure, snapshot, animation, export) and their operations in core areas (load.entry, load.url, session.save, canvas.lighting, …) come with the default spec and are typed as present, so await api.load.entry({ id: '1tqn' }) needs no !: reading one in a viewer whose spec left its feature out throws, naming the feature. The lazy ones (superpose, state, particles) and remote states are optional in the type, so check for them (api.superpose?.chains(...)) when you do not control the spec; api.area(id) and api.describe(id) ask for any.

The loaders share one vocabulary. Each that reads content (load.data, load.volume, load.mvs, load.svs, session.open) takes exactly one of url, data (text, 'base64,…', or bytes: a Uint8Array or an ArrayBuffer) and file (a File); none or several is invalid. load.url takes a url only, load.files several files. format is 'auto' by default: Mol*‘s format registry reads it from the extension of the address or the file (.bcif, .cif.gz, .mrc, .map, .ccp4, .dsn6, .mvsx, …), else from the data itself, and an operation that cannot tell fails invalid, naming the formats it takes. binary is optional: left out, it follows from the extension or the format (BinaryCIF, CCP4 maps, DSN6, DCD, XTC, TRR are binary). session.open also takes a state server’s id; load.snapshot is the same operation under the name the snapshot-url and snapshot-id URL parameters use.

packages/prism/viewer/_spec/operations.md lists every operation with its parameters and flags, written from the code.

Extensions add areas of their own, under their id. A script that imports an extension gets its area typed. See Extensions.

Examples

Section titled “Examples”

The values of each operation are described by api.describe(id) (below). Where a value takes a registry entry, such as a preset id or a color theme, the failure message and hint list the choices.

Reading

Section titled “Reading”

A read is an operation with a value and no history step. api.select.get(), api.component.list() and api.structure.list() return text in did and data in value. A few areas also expose a ReadonlyState to subscribe to: structure.loaded, canvas.state, history.steps, annotations.providers and animation.state. For the selection and the focus as states, use viewer.sources.interaction.

Targets

Section titled “Targets”

Operations that act on part of a structure take a target. A target is a string, and the same string means the same thing in the API, the commands and the assistant’s tools.

FormExamples
A keywordall, polymer, protein, nucleic, branched, ligand, ion, water, coarse
The person’s ownselection and focus: what is selected and focused now.
AddressesA, B:120, B:200-210, B:120A, C:122@OG1, A:10-20, C. Author numbering.
Query textresn HEM, resn HIS and chain A, within 5 of resn STI: PyMOL by default.

A string is read as a keyword, then as addresses, then as query text. Reading is lenient about spaces, case and a trailing comma. What cannot be read fails with the part that did not read and a hint.

Set language: 'vmd' | 'jmol' | 'molscript' to read the query text in another language. A target can also be schema items, for example { auth_asym_id: 'A', beg_auth_seq_id: 248, end_auth_seq_id: 256 }, or { molql: expression } with a MolScript expression as JSON. Whatever the form, everything compiles to MolQL, and that is what the history and the session record store.

When several structures are loaded, say which with structure: '1TQN', a label or a state ref. Without it an operation uses the structure you are working with: the focused one, else the one holding the selection. Past that, a target applies to every loaded structure, and an operation on one structure fails and lists them. Removing a structure always needs its name when several are loaded. The result says which it was.

Nodes

Section titled “Nodes”

Operations on cells of the state tree (state.*; a representation’s update, visibility and remove; volume.* and particles.*) take a node: a selector in the shape of CSS, compiled to Mol*‘s StateSelection.

PartExamples
Kindsdata, trajectory, model, structure, component, representation, volume, *
Attributes[label="1CBS"], [type=cartoon], [tag=mine] or .mine, [transformer$=component], #ref
Operators=, *= (contains), ^= (starts with), $= (ends with); text compares without case
States:hidden, :visible, :error, :not(...)
Combinatorsa space (anything below), > (a child), , (either)

A ref alone works too. An operation acts on every match of its kind as one step; one that needs a single cell (state.get, state.action) lists the matches when there are several. In scripts, node() from @molstar/prism-viewer/api writes the same text: node('component', { type: 'ligand' }).child('representation').

Origins

Section titled “Origins”

Every call has an origin that says who made it. viewer.api runs as script. api.as(origin) gives the same API for another:

KindUsed by
personThe commands and forms in the UI.
scriptviewer.api, and viewer.run.
agent (with a turn id)The assistant’s tools.
urlThe URL’s loading parameters.
linkThe sequence view acting on the 3D view.

History and the session record keep the origin of each step. The status column reports the results of a person’s and the URL’s calls, not a script’s.

History and undo

Section titled “History and undo”

The viewer has one undo history. Every undoable operation run is one step, and a checkpoint of the scene is taken before it. Undo restores the latest checkpoint.

  • Operations that change what you see and not the scene are not steps: select, focus, highlight, camera, view, trajectory frames, and reads. Undo does not restore the camera, the selection, the focus or the open panels.
  • A result that is unchanged makes no step. An operation that cannot be restored, such as an upload, makes no step either and is only recorded.
  • A run that fails or is aborted restores its checkpoint, so a load that fails half way leaves nothing behind.
  • Undo is not available while a run is in flight. Redo puts back what Undo took back, until a new step is made.
  • Changing the plugin outside the API (a script that calls a loader on viewer.plugin without run) still shows, but makes the steps before it unsafe: History marks them, and they can no longer be undone.
  • For a very large scene, the viewer turns per-step undo off and says so once.

Groups

Section titled “Groups”

api.group makes the calls inside it one step, and one group in the record:

The group fails as a whole if the work throws, returns a failed result, or a call inside fails: the checkpoint is restored and the result says so. { onFailure: 'continue' } undoes only the failed call and goes on. Calls an operation makes through its own ctx.api are part of its step in the same way.

For work that no operation covers yet, viewer.run(label, (plugin, api) => ...) is one step: it is recorded as one opaque run, and the calls it makes through api join it.

An assistant’s turn

Section titled “An assistant’s turn”

An assistant’s turn is one step, a group with its agent origin. api.history.undoTurn({ turn }) undoes it. If the person made steps after the turn, it fails with the code confirm; call again with discardLater: true to undo those too.

Describing operations

Section titled “Describing operations”

api.run(id, values?, options?) runs an operation by its id, which is how commands, tools and the run log name them. An id that does not exist gives a not-found result.

Events and state

Section titled “Events and state”

A run record has id, operation, title, values, origin, started, result, ms, step, group and nested.

The viewer’s other observables are viewer.state.ready, .busy, .working and .empty, viewer.events.hover, .click and .error, and viewer.managers.history (steps, canUndo, undoBlocked, running, checkpointing).

States are ReadonlyState: an rxjs Observable that replays its current value on subscribe and also has a synchronous .value. Events are plain observables that replay nothing. busy is the plugin’s flag, which comes on 750 ms late; working is true whenever anything is in progress now: an operation from its start, a lazy extension loading, the plugin updating.

What is stable

Section titled “What is stable”

The core areas and the built-in features’ are the public contract: their ids, values and results follow semver once the package is released. Areas that extensions add, and viewer.plugin, carry no such promise.
